# react-qa-service Harness Engineering 规则

本文档用于约束 `Codex` 在本项目中的协作方式。目标不是限制生成能力，而是避免项目在持续迭代中变乱、变脆、变得难维护。

## 1. 目标

- 让改动尽量小而闭环
- 让高频 commit 仍然可读、可回滚、可跨设备同步
- 让业务代码、测试、文档能一起演进
- 只限制高风险行为，不对低风险实现细节做过度约束

## 2. 适用范围

- 后端：`app/`
- 前端：`src/`
- 测试：`tests/`
- 文档：`docs/`
- 迁移和运行配置：`migrations/`、`pyproject.toml`、`package.json`

## 3. Codex 默认工作方式

每次任务默认按以下顺序执行：

1. 先阅读相关文件，再决定怎么改
2. 优先做最小范围的闭环改动
3. 尽量复用现有架构、脚本、测试和命名方式
4. 改完后执行与改动范围匹配的最小验证
5. 输出变更摘要、验证结果、剩余风险

如果任务描述不完整，优先根据仓库现状做保守实现，不主动扩大范围。

## 4. 允许行为

- 在现有目录和模块边界内做增量开发
- 修复 bug 时同步补测试或说明覆盖点
- 补充必要注释、类型、文档和运行说明
- 为了稳定性做小范围重构
- 复用已有命令，如 `npm run lint`、`npm run typecheck`、`npm run test`、`npm run build`

## 5. 禁止行为

- 无明确收益的大范围架构重写
- 把多个无关目标混在一次改动里
- 跨层直接调用，绕开已有 service / repository / API 边界
- 未说明风险就修改认证、会话、数据库迁移、主流程编排
- 修改接口或行为后不补验证、不更新相关文档
- 为了“看起来更整洁”而顺手重排大量无关代码

## 6. 变更分级

### L1：低风险改动

适用场景：

- 文案、注释、样式、小范围显示修复
- 不改变接口和主要逻辑的局部调整

要求：

- 保持单一目的
- 可不加测试，但不能破坏现有行为

### L2：常规功能或修复

适用场景：

- 单模块逻辑修改
- 小范围 API 行为修复
- 单一页面交互调整

要求：

- 必须有对应验证
- 能补测试时优先补测试
- 若不补测试，必须在结果说明里明确原因

### L3：高风险业务改动

适用场景：

- 认证与授权
- 会话管理
- 数据库存储与迁移
- `DocumentAgentService` / `ReActEngine` / 主链路编排
- API 契约变化

要求：

- 改动前先明确影响面
- 同步更新测试和文档
- 不允许夹带无关重构

### L4：架构级改造

适用场景：

- 大范围目录重组
- 核心依赖替换或升级策略变更
- 存储方案、工程工具链、主流程模型的大改

要求：

- 不作为日常 Codex 任务直接执行
- 必须单独立项、单独分支、单独评审

## 7. 本项目高风险区域

以下区域默认按 `L3` 对待：

- `app/main.py`
- `app/api/v1/`
- `app/services/`
- `app/db/`
- `app/repositories/`
- `migrations/`

尤其是以下主题：

- 登录、鉴权、token、session、logout、audit log
- PostgreSQL / Redis 双写与读切换
- QA / Summary / retrieval / rerank / planner 主链路

## 8. 测试与验证规则

Codex 不要求每次全量验证，但必须做“与改动匹配”的最小验证。

推荐映射：

- Python 逻辑改动：`npm run lint`、`npm run typecheck`、`npm run test`
- 前端展示改动：至少 `npm run build`
- 高风险主链路改动：优先运行对应测试，必要时补全量 `npm run validate`

如果因为环境限制无法执行验证，必须明确写出未执行项和风险。

## 9. 文档同步规则

出现以下情况时，文档应同步更新：

- 新增或修改开发约定
- 修改运行方式、配置项、验证命令
- 修改 API、认证行为、存储行为、主流程策略
- 引入新的手工操作步骤

文档只写必要信息，不把一次小改动扩展成大而全说明。

## 10. 简明判断标准

满足以下几点时，说明这次改动是合格的：

- 目标单一
- 范围清晰
- 改动边界符合当前架构
- 有最小验证
- 需要同步的测试和文档已同步
- commit message 能说明这次改了什么

如果某个实现会明显提高复杂度，但不能直接提升稳定性、可维护性或交付效率，默认不做。
